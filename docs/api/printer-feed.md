# Printer order feed

The printer app polls `GET /api/orders/printer-feed` with its `X-Api-Key` and registered `X-Device-Id`. `modifiedSince` is the incremental timestamp boundary; `orderCursor` drains the stable 50-order pages without changing that boundary. The legacy response shape is unchanged.

For a device-aware poll with `modifiedSince`, the feed normally returns confirmed, kitchen-released orders changed after the boundary, including queued routes assigned to that device. A required route that remains `Queued` can also be recovered when its last queue-state timestamp (`UpdatedAt`, otherwise `CreatedAt`) is within `OrderRouting:RequiredQueuedRouteRecoveryHours`, inclusive. The default is **1 hour**, matching the deployed printer app's persistent completed-order deduplication window. The setting accepts 1–24 hours; values above one hour are an explicit operator reconciliation choice, not a routine backlog replay. This recovery is read-only: it preserves the existing route/job identity and does not reset terminal acknowledgements or requeue work.

New order cursors freeze the recovery cutoff and its server issue time, so every page in one drain uses the same inclusive boundary even if time advances between requests. Cursors expire after `OrderRouting:RequiredQueuedRouteRecoveryCursorLifetimeMinutes` (15 minutes by default); restart the poll from its original `modifiedSince` if a drain expires. The API accepts legacy date/id cursors, but since they carry no recovery fence, their continuation begins with a fresh configured window. Cursor timestamps are checked against the current recovery-window setting and cannot request an older cutoff.

Queued work can appear on repeated polls until the device acknowledges a terminal result. Delivery is at least once: a missing server acknowledgement does not prove that paper was not printed. The printer app persists acknowledgement retries, but its completed-order deduplication expires after one hour and the acknowledgement queue is bounded. If an acknowledgement is lost after physical output, replaying queued work can print a duplicate. Required queued routes older than the configured recovery window remain available for reconciliation; confirm paper status before manually requeueing or printing them.

When routing is active, a request without `X-Device-Id` keeps the legacy unrouted-order projection and does not receive assigned printer routes. A request with a device ID receives only that device's queued routes. `Printed`, `Skipped`, `Failed`, and other non-queued states are not re-delivered as queued work.
